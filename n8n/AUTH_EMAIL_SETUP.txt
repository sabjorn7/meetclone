Flow
Frontend signUp -> existing auth.users/profile trigger -> signed GoTrue hook
-> verify original bytes and timestamp -> atomically claim opaque delivery key
-> existing Unisender sendEmail API -> record accepted/failed/uncertain -> JSON reply.
GoTrue owns token generation and verification. The workflow uses the already generated
email_data.token_hash in the native GET /auth/v1/verify?token=...&type=signup URL.
There is no second signup, createUser, generateLink, UUID rewrite or profile write.
Password never reaches this hook. The account/profile transaction is still GoTrue's.
Role metadata.nickname and its existing Специалист -> Ученик mapping are preserved.

Transport deadline, failures and duplicate protection
- Verify HMAC-SHA256 Standard Webhooks signature on ORIGINAL body bytes, not reserialized JSON.
- Reject missing/malformed/stale/tampered signatures, unknown actions and external redirects.
- Only the fixed MeetGuru sender, subject, recipient from signed user.email and callback are used.
- Claim RPC timeout <=600ms; Unisender <=2000ms; finish RPC <=600ms. Each timeout is shortened
  by the remaining hook budget. No per-node retries and no Wait/queue/email batch in the hook.
- n8n needs a warm execution path and synchronized clocks. These budgets are not a guarantee
  of delivery under a slow provider/queue; slow/unavailable infrastructure fails closed.
- Unisender uses HTTPS POST form body, never API key/body/token in query parameters.
  error_checking=1 is required. Only the one expected recipient with a valid message id and
  no reported errors counts as accepted. HTTP 200 alone does not count as success.
- Only accepted AND durably recorded delivery returns 200 application/json {}.
  This is necessary in v2.171.0, whose hook decoder does not accept an empty response body.
- Atomic unique delivery key = SHA256(signup + user UUID + email + GoTrue token hash).
  The table stores only this opaque key, owner nonce, state and timestamps. No raw email,
  password, OTP, token hash or confirmation URL is stored there.
- A GoTrue retry with a NEW webhook-id sees the same key and does not send another letter.
  A true auth.resend gets a fresh token and therefore a new key. No password is needed.
- Concurrent sending, failed, uncertain and abandoned attempts are never reclaimed for
  automatic sending. A timeout can mean the provider accepted the first request.
  The user can request a NEW confirmation via the throttled public resend API.
- Exactly-once external email delivery is impossible without provider idempotency: a provider
  may accept mail while its response is lost, or Auth may roll back after external acceptance.
  This design avoids an automatic second send of the same token and never falsely confirms
  an account or claims successful delivery after an unknown provider result.
- Retain ledger tombstones for at least the maximum token lifetime plus replay window.
  With OTP_EXP<=86400, admin cleanup of rows older than 48 hours is sufficient. No cleanup
  job was scheduled; do not prune if actual token lifetime is longer.
- API acceptance is not inbox delivery. Existing sender/domain authorization, list suppression,
  unsubscribe/block rules, quota and actual delivery latency must be checked with an explicitly
  approved test account before rollout. Do not reuse marketing body/template fields blindly.

Frontend behavior
- Domain typo suggestion is optional and never rewrites email without a click.
- No-session signup shows Проверьте почту, clears password refs and does not call the old
  email+password notification hook. Successful session branch remains compatible with the
  current autoconfirm configuration; after enabling confirmation it is not used for new users.
- Callback uses the EXISTING SDK/client session, removes the callback hash and goes to /welcome.
- Expired/missing session stays on login with an editable resend email field.
- Resend uses auth.resend(type=signup), explicit same-origin callback, 60-second UI cooldown,
  one in-flight request, and a 12-second UI timeout. Server limits remain authoritative.
- Provider/hook errors do not show Проверьте почту or redirect to welcome. Error text is fixed
  Russian copy; raw transport errors are not displayed or logged by these new components.
- Password and verification tokens are never put into storage or a delayed welcome webhook.
