Problem and behavior
The chat previously fetched the oldest 200 visible messages, so later messages
were saved but never displayed. Live chats now request created_at DESC, id DESC,
limit 200 and reverse the response for chronological display. Speaker and viewer
use the same small read helper. New arrivals are detected by ID even when the
window remains at 200. The existing 7-second HTTP poll remains.

Ended streams fetch all visible messages in sequential pages of up to 200,
ordered by created_at DESC, id DESC. Each subsequent page uses a strict older-than
cursor on the original timestamp string and UUID; the complete result is reversed.
There is no offset and no total limit. Reading continues until an empty page,
including if the server returns smaller pages. After the initial full replay read,
subsequent 7-second polls request only rows strictly newer than the last loaded
(created_at,id), in ascending order, paged until empty. New rows are appended;
an empty response does not replace the current array or scroll it. Cursor and
history initialization reset when the chat closes or switches streams. An empty
initial history is supported. Partial results/errors never advance the cursor.
Hidden-link RPC behavior is unchanged. Partial history is never substituted after
a page failure.
Deleted messages remain excluded by the original neq(deleted,true) condition.

Both interfaces retain the feed and show a quiet status after refresh failure,
clearing it on success. Speaker send failures show an error and retain the draft.
Returning to a visible tab triggers refresh. Slow requests are serialized, one
refresh can be queued, and obsolete responses cannot restore a stopped chat.
The existing access checks and capability RPC path remain in place.

Scope limitation: hidden/unlisted link chat
get_stream_link_messages is a server RPC with an oldest-200 cap and no cursor.
Its capability path is unchanged; it is not bypassed with table reads. Unlimited
history/latest-window correction for that separate path requires a backend scope
decision. No SQL/RPC/RLS edits were authorized or made. The audited public stream
d86a0c44-247f-4c24-954e-7fa7987df82f uses the ordinary path fixed here.

Tradeoff
The full replay history is read once per opening, followed only by new rows.
Long histories still require browser memory. Requests do not overlap; there is no
new delivery service, server cache or pagination UI. All fetched rows retain the
existing deleted-message filter. Local delete still removes a message immediately.
Because follow-up reads fetch only newer rows, deletions of older loaded messages
by other users are reflected on reopening (full read), not by incremental polls.
